# 차량 여행 방탈출 앱: Codex 개발 지침

작성일: 2026-11-12  
대상 환경: Android Studio / Pleos Connect 에뮬레이터  
문서 목적: 다른 Codex 세션에 전달해 새 Android 프로젝트의 기본 기능을 구현하기 위한 작업 명세

> 이 문서는 구현 요청서입니다. 설명이나 계획만 제출하지 말고, 아래 범위의 Android 프로젝트와 테스트를 실제로 작성하십시오. 실행 환경에 접근할 수 없다면 구현 가능한 작업은 진행하고, 빌드·에뮬레이터 검증의 미실행 항목과 이유를 명시하십시오.

## 1. 사용자가 확정한 범위

| 항목 | 결정 |
| --- | --- |
| 프로젝트 상태 | 새 프로젝트 생성 |
| 첫 구현 범위 | 게임 기본 기능과 도착·주차 시뮬레이션 |
| 개발 환경 | Android Studio와 Pleos Connect 에뮬레이터 |
| 서버 | 사용하지 않음 |
| 계정 | 로그인·회원가입 없음 |
| 저장 | 기기 내부 저장 |
| 콘텐츠 | 스토리·좀비 설정·실제 관광지·여행 코스 구성은 보류 |
| 실제 위치·지도 | 이번 구현에서 제외 |
| 실제 차량 기능 | 이번 구현에서 제외; 나중에 연결 가능한 경계만 마련 |

프로젝트의 장기 목적은 자동차 여행 중 경유지에 도착하면 주차한 차량 안에서 짧은 방탈출을 하는 것입니다. 지금은 그 경험을 지탱할 게임 기능만 구현합니다.

아래의 앱 이름, 패키지명, 테스트 경유지, 정답, UI 구성은 별도 질문 없이 진행하기 위한 개발 기본값입니다. 최종 상품 기획이나 확정된 콘텐츠로 취급하지 마십시오.

## 2. 이번 작업의 완성 모습

Pleos 에뮬레이터에 APK를 설치해 다음 흐름을 끝까지 실행할 수 있어야 합니다.

1. 앱을 실행해 새 테스트 게임을 시작합니다.
2. 테스트 경유지 목록에서 현재 진행 가능한 경유지를 확인합니다.
3. 개발용 패널에서 현재 경유지 도착을 시뮬레이션합니다.
4. 주차 상태를 `PARKED`로 설정하면 퍼즐 입력이 활성화됩니다.
5. 자물쇠를 풀거나, 힌트를 확인하거나, 건너뛰기를 선택합니다.
6. 획득한 단서를 단서함에서 확인합니다.
7. 다음 경유지에서도 같은 과정을 반복합니다.
8. 세 경유지를 처리하면 완료 화면에 해결·건너뛰기 내역이 표시됩니다.
9. 진행 중 앱 프로세스를 종료하고 다시 실행해도 마지막으로 저장 완료된 진행이 복원됩니다.

이동 중인 실제 차량에서 사용할 수 있는 완성품은 아닙니다. 화면에는 `개발용 시뮬레이션` 표시를 유지하고, 가짜 도착·주차 상태를 실제 센서 연동으로 설명하지 마십시오.

## 3. 범위 통제

### 반드시 구현

- 네이티브 Android 앱의 생성, 빌드, 실행 가능한 진입 Activity.
- 테스트 패키지 선택 또는 시작, 이어하기, 새 게임 초기화.
- 순서가 있는 테스트 경유지 3개와 진행 잠금.
- 숫자형·순서형·상태 조합형 자물쇠 각 1종.
- 오답 피드백, 입력 초기화, 정답 처리, 중복 완료 방지.
- 퍼즐별 단계별 힌트, 정답 보기, 건너뛰기.
- 단서 보상, 단서함 목록·상세 화면.
- 진행·힌트 사용·오답 횟수의 로컬 저장과 복원.
- 개발용 도착·주차 시뮬레이션과 플레이 가능 여부 판정.
- 빈 상태, 로딩, 저장 실패, 데이터 오류 화면.
- 핵심 로직 테스트, 에뮬레이터 확인 절차, 실행 문서.

### 구현하지 않음

- 좀비 스토리, 관광 정보, 실제 지역 패키지, 분기 엔딩.
- AI API, 스토리 자동 생성, 챗봇, 음성 합성.
- 실제 GPS, 지오펜싱, 지도 화면, 길찾기·경로 최적화.
- 실제 차 문·창문·조명·공조 제어, 차량 센서 데이터 읽기.
- BLE 자물쇠, 물리적 보관함, QR·카메라 인식.
- 서버, Firebase, 인증, 결제, 온라인 동기화, 멀티플레이.
- 시간 제한, 점수 경쟁, 이동 속도 보상, 백그라운드 위치 추적.
- 스토어 제출, 배포 서명, 실차 지원 보장.

향후 기능을 위해 구현하지 않는 서비스의 빈 클래스·빈 화면·과도한 설정 메뉴를 만들지 마십시오. 실제로 교체가 필요한 데이터·저장·도착·주차 경계만 분리하십시오.

## 4. 환경과 기술 선택

### 4.1 기본 구성

| 항목 | 개발 기본값 |
| --- | --- |
| 프로젝트 이름 / 앱 표시명 | `RoadEscape` / `차량 방탈출 데모` |
| 임시 applicationId / namespace | `com.example.roadescape` |
| 언어 | Kotlin |
| UI | Jetpack Compose + Material 3 |
| 구조 | 단일 `:app` 모듈, UI / 게임 로직 / 데이터 책임 분리 |
| 상태 | ViewModel + StateFlow, 단방향 이벤트 처리 |
| 화면 이동 | 프로젝트와 호환되는 안정 버전의 Compose용 Navigation |
| 비동기 | Kotlin Coroutines |
| 콘텐츠 | assets의 정적 JSON + kotlinx.serialization |
| 진행 저장 | Typed DataStore + JSON Serializer로 작은 진행 스냅샷 저장 |
| 의존성 관리 | Gradle Kotlin DSL + Version Catalog |
| DI | 간단한 수동 생성자 주입과 앱 컨테이너 |
| minSdk | 28을 기본값으로 설정 |
| 네트워크 | 실행 중 네트워크 연결이나 API 키 불필요 |

데이터 규모가 작으므로 초기 버전에 Room, Hilt, 별도 서버를 추가하지 않습니다. 사용자 요구나 검증된 기술적 사유 없이 기술 스택을 확대하지 마십시오.

### 4.2 실제 프로젝트 생성 전 확인

1. 작업 폴더와 적용되는 `AGENTS.md`, 설치된 Java, Android SDK, Gradle/Android Studio 환경을 확인합니다.
2. 이미 생성된 Android 파일이 있으면 삭제하거나 덮어쓰지 말고 구조를 확인한 뒤 활용합니다.
3. 공식 Pleos 안내의 Automotive/Car Empty Activity 흐름을 기준으로 설치 가능한 네이티브 Activity 앱을 만듭니다. Android Auto 휴대전화 투사 앱이나 웹뷰 앱으로 대체하지 않습니다. 템플릿 명칭은 Android Studio 버전에 따라 다를 수 있습니다. [S1]
4. `minSdk`, `compileSdk`, `targetSdk`와 AGP·Gradle·JDK·Kotlin·Compose 조합을 구분해 확인하고 실제 빌드 가능한 버전으로 고정합니다. `+`나 `latest.release` 같은 동적 버전을 사용하지 않습니다.
5. 에뮬레이터의 API 수준이 `compileSdk`와 같아야 한다고 가정하지 않습니다. 의존성의 최소 요구 수준과 실행 호환성을 각각 검토합니다.
6. 정상 Gradle Wrapper를 포함합니다. wrapper JAR 누락이나 가짜 실행 파일로 빌드 가능한 것처럼 표시하지 않습니다.
7. Windows 사용자를 위한 `gradlew.bat`와 Unix 계열용 `gradlew` 실행 방법을 모두 문서화합니다. `local.properties`의 개인 SDK 경로는 공유 코드에 넣지 않습니다.

공식 Pleos 설치 문서에서 확인한 기준은 API 34 시스템 이미지와 에뮬레이터 2.1.0, `minSdk` 28 이상입니다. 실제 사용자가 설치한 버전은 아직 확인되지 않았으므로 이것을 설치 완료 사실로 취급하지 마십시오. 정상 작동하는 기존 AVD를 임의로 삭제하거나 초기화하지 않습니다. [S2]

### 4.3 Pleos SDK에 관한 원칙

이번 단계는 Pleos 에뮬레이터에서 게임 앱을 실행하는 단계이며, Pleos Vehicle SDK를 사용해 차량을 제어하는 단계가 아닙니다.

- 실제 차량 API를 호출하지 않으므로 Vehicle SDK·NaviHelper·FusedLocation 의존성이나 권한을 선제적으로 추가하지 않습니다.
- Pleos 에뮬레이터의 Virtual Console을 조작해도 이번 앱의 가짜 주차·도착 상태와 자동 연결되지 않습니다. 앱 내부 개발 패널로 테스트합니다.
- 추후 차량 연동 시에만 공식 문서로 의존성·권한·지원 영역·콜백을 확인하고 어댑터를 구현합니다.
- SDK 초기화 성공과 기능 지원·실제 상태 수신 성공은 다른 상태입니다. 문서상 API 존재만으로 특정 차량에서 지원된다고 가정하지 않습니다. [S3]
- 현재 없는 Pleos API 이름, 패키지, 권한 문자열을 추정해 작성하지 않습니다.

## 5. 화면 요구사항

| 화면 | 필수 내용과 행동 |
| --- | --- |
| 시작 화면 | 테스트 패키지 1개, 새 게임, 저장된 게임이 있으면 이어하기 |
| 경유지 목록 | 3개 경유지, 현재 진행 가능 항목, 방문 확인 여부, 해결·건너뛰기 상태 |
| 퍼즐 화면 | 제목, 지시문, 단서, 해당 자물쇠, 제출·지우기, 힌트·정답 보기·건너뛰기 |
| 단서함 | 얻은 단서 목록, 출처 경유지, 단서 상세, 비어 있을 때 안내 |
| 완료 화면 | 해결 수, 건너뛰기 수, 힌트·정답 공개 사용 내역, 새 게임 |
| 개발용 패널 | 현재 경유지 도착 처리, `PARKED / DRIVING / UNKNOWN` 전환, 현재 게이트 상태 |

UI 기본 원칙:

- 한국어 UI를 기본으로 하고 공통 문구는 문자열 리소스로 관리합니다.
- Pleos의 가로형 화면을 우선하되 특정 픽셀 크기 하나로 고정하지 않습니다.
- 넓은 화면에서는 경유지·단서 정보와 퍼즐을 나란히 배치하고, 공간이 부족하면 스크롤이나 단일 열로 전환합니다.
- 개발 기준으로 터치 영역은 최소 56dp를 확보합니다. 이는 이 프로젝트의 설계값이며 Pleos 공식 최소 규격이라는 의미는 아닙니다.
- 상태는 색만으로 구분하지 않고 텍스트·아이콘을 함께 씁니다.
- 시스템 바·화면 인셋을 처리하고 퍼즐 버튼이 가려지거나 잘리지 않도록 합니다.
- 숫자 입력은 화면 키패드, 순서 입력은 기호 버튼, 상태 조합 입력은 단계 선택 버튼으로 구현해 외부 키보드가 없어도 완주 가능해야 합니다.
- 과도한 애니메이션·배경음·깜빡임은 넣지 않습니다. 성공·오답은 텍스트와 짧은 시각 효과로 전달합니다.
- 로딩 중에는 기존 데이터가 없다고 판단해 새 게임으로 덮어쓰지 않습니다.

## 6. 검증용 데이터와 자물쇠

### 6.1 최소 테스트 패키지

`assets/demo_package.json`에 아래와 동등한 검증 데이터를 넣습니다. 실제 장소·좌표·스토리는 사용하지 않습니다.

| 경유지 ID | 표시명 | 퍼즐 ID / 종류 | 정답 | 성공 또는 건너뛰기 후 제공 단서 |
| --- | --- | --- | --- | --- |
| `cp_01` | 테스트 경유지 1 | `p_01` / `NUMERIC` | 문자열 `0427` | `clue_01` / 테스트 단서 A |
| `cp_02` | 테스트 경유지 2 | `p_02` / `SEQUENCE` | `UP, RIGHT, DOWN, LEFT` | `clue_02` / 테스트 단서 B |
| `cp_03` | 테스트 경유지 3 | `p_03` / `STATE_COMBINATION` | `channel = 3`, `level = 2` | `clue_03` / 테스트 단서 C |

테스트 단서는 후속 퍼즐의 필수 정답으로 연결하지 않습니다. 보상·보관함 기능만 검증합니다. 각 퍼즐의 지시문만 읽어도 정답을 도출할 수 있도록 구성합니다.

- 숫자형 지시문 예: `카드에 적힌 0, 4, 2, 7을 왼쪽부터 입력하세요.`
- 순서형 지시문 예: `위 → 오른쪽 → 아래 → 왼쪽 순서로 버튼을 누르세요.`
- 상태 조합형 지시문 예: `가상 장치의 채널을 3, 레벨을 2로 맞추세요.`

### 6.2 숫자형

- 정답과 입력을 문자열로 취급해 선행 0을 보존합니다.
- 테스트 퍼즐은 정확히 4자리만 받습니다. 자리 수는 퍼즐 정의로 바꿀 수 있어야 합니다.
- 숫자 추가, 한 글자 삭제, 전체 지우기, 제출을 지원합니다.
- 길이가 맞지 않은 입력은 형식 오류이며 오답 횟수를 올리지 않습니다.
- 형식이 유효한 제출이 정답과 다를 때만 오답 횟수를 1 증가시킵니다.

### 6.3 순서형

- 기호는 `UP / RIGHT / DOWN / LEFT`처럼 안정된 ID로 저장하고 UI에서 방향 아이콘과 한국어 이름을 매핑합니다.
- 누른 순서가 화면에 표시되어야 하며 마지막 입력 삭제·전체 지우기를 지원합니다.
- 정답 길이만큼 입력한 후 명시적으로 제출합니다. 길이가 맞지 않으면 형식 오류입니다.
- 순서와 길이 전체를 비교합니다. 같은 기호가 반복되는 다른 퍼즐도 데이터로 표현할 수 있어야 합니다.

### 6.4 상태 조합형

- 두 가상 설정 `channel`, `level`을 각각 정수 0~5 범위에서 조작합니다.
- 초깃값은 각각 0이며, 두 값이 모두 정답일 때 제출하면 해결됩니다.
- UI에 `가상 장치`임을 표시합니다. 실제 공조·차량 센서를 읽지 않습니다.
- 입력 범위를 벗어난 값이나 필요한 키가 빠진 입력은 형식 오류로 처리합니다.
- UI의 마지막 제출 순간에만 판정합니다. recomposition이나 값 변경만으로 보상이 지급되지 않아야 합니다.

### 6.5 공통 판정

- `LockEvaluator`는 퍼즐 정의와 입력을 받아 `InvalidInput / Incorrect / Correct`와 같은 명시적 결과를 반환합니다.
- Android Context·Compose·저장소에 의존하지 않는 순수 Kotlin 로직으로 만듭니다.
- 실제 데이터 수정은 게임 진행 처리 계층이 담당합니다. 평가 함수 자체가 보상을 지급하거나 저장하지 않습니다.
- 해결된 퍼즐의 반복 제출은 진행·오답 횟수·보상을 변경하지 않습니다.
- 로컬 게임이므로 정답이 APK 안에 들어가는 것은 허용합니다. 이를 보안이 필요한 실제 잠금 장치로 설명하지 않습니다.

## 7. 힌트·정답 공개·건너뛰기

각 퍼즐은 2단계 힌트와 별도의 정답 해설을 갖습니다.

| 행동 | 처리 |
| --- | --- |
| 힌트 보기 | 다음 단계 힌트 공개, 공개한 단계 수 저장 |
| 이미 본 힌트 다시 보기 | 추가 사용 횟수 증가 없음 |
| 정답 보기 | 확인 후 정답과 짧은 해설 공개, `answerRevealed = true` 저장 |
| 정답을 본 뒤 직접 제출 | 입력이 맞으면 `SOLVED`, 정답 공개 사용 사실은 유지 |
| 건너뛰기 | 확인 후 `SKIPPED`, 필요한 보상은 지급하고 다음 경유지 진행 허용 |

정답 공개만으로 퍼즐을 해결 처리하지 않습니다. 건너뛰기는 성공과 다른 결과이며 완료 화면에서도 구분합니다. 힌트·정답·건너뛰기는 모두 현재 퍼즐의 플레이 가능 조건을 만족할 때만 변경할 수 있습니다.

이미 확보한 단서가 있으면 재지급하지 않습니다. 건너뛰기로 받은 단서는 그 경위를 저장해 상세 화면에서 구분할 수 있도록 합니다.

## 8. 진행 상태와 도착·주차 게이트

### 8.1 경유지 진행 상태

각 경유지는 `NOT_STARTED / IN_PROGRESS / SOLVED / SKIPPED` 중 하나입니다. `SOLVED`와 `SKIPPED`는 완료 처리된 상태입니다.

현재 진행 가능한 경유지는 목록에서 앞선 모든 경유지가 완료 처리된 첫 미완료 경유지입니다. 이 값은 저장된 상태에서 계산하고 별도의 중복 상태로 관리하지 않는 편을 우선합니다.

| 이벤트 | 조건 | 결과 |
| --- | --- | --- |
| 새 게임 | 사용자가 시작 또는 초기화 확정 | 모든 경유지 초기화, 새 `sessionId` 생성 |
| 도착 시뮬레이션 | 현재 경유지에 대한 개발 이벤트 | 해당 경유지의 방문 기록 저장; 중복 도착은 무시 |
| 퍼즐 시작 | 방문 기록 존재, 현재 경유지, 주차 상태 정상 | `NOT_STARTED`를 `IN_PROGRESS`로 변경 |
| 유효한 오답 | 플레이 가능, 미완료 | 오답 횟수 증가, 진행 유지 |
| 정답 | 플레이 가능, 미완료 | `SOLVED`, 보상 지급, 다음 경유지 진행 가능 |
| 건너뛰기 | 플레이 가능, 사용자 확인, 미완료 | `SKIPPED`, 보상 지급, 다음 경유지 진행 가능 |
| 전체 완료 | 모든 경유지가 `SOLVED` 또는 `SKIPPED` | 완료 화면 표시 |

방문 기록은 “이 세션에서 도착 확인을 한 적 있음”을 뜻합니다. 현재 실시간 위치를 뜻하지 않습니다. 경유지가 바뀌면 다음 경유지에 대해 새 도착 이벤트가 필요하며 이전 경유지의 도착을 재사용하지 않습니다.

### 8.2 주차 상태

- 앱 소유 인터페이스 `ParkingStateProvider`에서 `PARKED / DRIVING / UNKNOWN` 상태를 받습니다.
- 초기 상태는 `UNKNOWN`입니다. 알 수 없는 상태를 주차로 간주하지 않습니다.
- 이번 구현은 debug 전용 가짜 구현에서 상태를 바꿉니다.
- 주차 상태는 저장된 게임 진행에서 복원하지 않습니다. 프로세스 재시작 시 다시 `UNKNOWN`입니다.
- 앱이 백그라운드로 나가면 가짜 주차 확인은 무효화하고, 돌아오면 개발 패널에서 다시 확인하게 합니다.

퍼즐 입력 활성화 조건은 다음과 같습니다.

`앱이 foreground임 AND 주차 상태가 PARKED임 AND 현재 경유지의 방문 기록이 있음 AND 현재 퍼즐이 미완료임 AND 저장 오류/로딩이 없음`

조건을 만족하지 않으면 이유를 표시합니다. `도착 확인 필요`, `주차 상태 확인 필요`, `주행 상태: 게임 일시 중지`, `저장 문제 해결 필요`를 구분합니다.

`DRIVING` 또는 `UNKNOWN`으로 바뀌면 퍼즐·단서·힌트 내용을 가리는 중단 화면을 표시하고 진행 변경 명령을 막습니다. 개발 패널의 상태 변경은 debug 환경에서 계속 가능해야 합니다. 다시 `PARKED`가 되면 기존 진행에서 재개합니다.

UI 버튼 비활성화만으로 막지 말고 게임 이벤트 처리 계층에서도 게이트를 확인합니다. 주차 변경·답안 제출 이벤트를 순서대로 처리하고, 중단 상태를 처리한 뒤 도착한 답안은 거절합니다. 중단보다 먼저 정상 처리·저장된 해결 결과는 되돌리지 않습니다.

### 8.3 개발용 패널

- `src/debug` 등 debug 빌드 전용 소스에 배치합니다.
- 현재 경유지 도착 처리, 주차 상태 변경, 현재 세션·경유지·게이트 상태 확인을 제공합니다.
- 미래 경유지를 임의 완료 처리하거나 순서 제한을 우회하는 기능은 만들지 않습니다.
- 진행 초기화는 확인 후 새 게임을 시작하는 동일한 로직을 호출합니다.
- release 빌드에는 개발 패널과 가짜 입력 제공자를 포함하지 않습니다. 실제 제공자가 아직 없으므로 주차 상태는 `UNKNOWN`으로 유지되고 플레이가 허용되지 않아야 합니다.
- release 빌드가 가능하다는 사실을 실차 출시 가능하다는 의미로 설명하지 않습니다.

## 9. 데이터 모델과 저장 규칙

아래는 의미를 고정하기 위한 모델 요구사항입니다. 클래스명은 유지하는 것을 권장하지만 구현상 더 적절한 이름으로 조정할 수 있습니다.

| 모델 | 주요 필드 |
| --- | --- |
| `GamePackage` | `id`, `contentVersion`, `title`, 순서가 있는 `checkpoints` |
| `CheckpointDefinition` | `id`, `title`, `puzzleId` |
| `PuzzleDefinition` | `id`, `type`, `prompt`, 타입별 설정·정답, `hints`, `solution`, `rewardClueIds` |
| `ClueDefinition` | `id`, `title`, `body` |
| `GameSession` | `schemaVersion`, `sessionId`, `packageId`, `contentVersion`, 경유지 진행, 보상 내역 |
| `CheckpointProgress` | `checkpointId`, `status`, `arrivedAt`, `wrongAttempts`, `revealedHintCount`, `answerRevealed` |
| `AcquiredClue` | `clueId`, `sourceCheckpointId`, `acquisitionType` |

타입별 퍼즐 정의·입력은 sealed class 등으로 명확히 구분하십시오. 임의 문자열 타입에 모든 nullable 필드를 몰아넣고 화면마다 강제 변환하는 방식은 피합니다.

저장 요구사항:

1. 세션은 한 번에 하나만 유지합니다. 다중 세이브 슬롯은 만들지 않습니다.
2. `GameRepository`에서 Typed DataStore의 단일 진행 스냅샷을 관리합니다. 같은 파일의 DataStore 인스턴스를 여러 개 만들지 않습니다. [S5]
3. 정답 처리·경유지 완료·단서 보상은 하나의 `updateData` 갱신으로 저장합니다. 성공 화면은 저장 성공 후 표시합니다.
4. UI 이벤트는 직렬 처리하고, 저장 중 중복 제출을 차단합니다. `sessionId + puzzleId`로 오래된 화면의 이벤트와 초기화 이전 이벤트를 거절합니다.
5. 힌트 공개·정답 공개·오답·도착·건너뛰기도 상태 변경 시 저장합니다. 앱 종료 시점에만 저장하지 않습니다.
6. `remember`나 ViewModel만으로 장기 저장을 대체하지 않습니다. 반대로 키패드 입력 한 글자마다 영구 저장할 필요는 없습니다.
7. 입력 중인 초안은 화면 회전·일시적 화면 복귀에 유지할 수 있지만, 프로세스 재시작 시 초기화되어도 됩니다. README에서 이 동작을 명시합니다.
8. 읽기·쓰기 실패 시 오류와 재시도 방법을 제공하고 진행을 자동 초기화하지 않습니다. 저장 실패 중의 추가 진행 변경은 차단합니다.
9. 손상된 데이터 또는 지원하지 않는 `schemaVersion`은 자동 덮어쓰기하지 않습니다. 원본을 보존한 채 복구 실패를 알리고 사용자가 명시적으로 초기화를 선택할 수 있게 합니다.
10. 콘텐츠 버전 불일치 시 ID를 임의로 새 콘텐츠에 끼워 맞추지 않습니다. 이번 단계는 자동 마이그레이션 대신 새 게임 안내로 처리해도 됩니다.
11. 정적 JSON의 중복 ID, 존재하지 않는 퍼즐·단서 참조, 지원하지 않는 퍼즐 타입, 잘못된 정답·범위를 앱 초기화 때 검증합니다. 잘못된 데이터로 게임을 시작시키지 않습니다.

## 10. 책임 분리와 파일 구성

단일 `:app` 모듈 내에서 다음 책임을 분리합니다. 필요한 실제 파일만 만들고 이름뿐인 추상화 계층을 늘리지 않습니다.

| 경로 예시 | 책임 |
| --- | --- |
| `model/` | 콘텐츠·진행·입력·결과 모델 |
| `game/LockEvaluator.kt` | 타입별 순수 자물쇠 판정 |
| `game/GameController.kt` | 진행 전이, 게이트 검증, 중복 이벤트 차단 |
| `data/PackageRepository.kt` | assets 로딩과 콘텐츠 검증 |
| `data/GameRepository.kt` | 세션 저장·복원·초기화 |
| `platform/ArrivalProvider.kt` | 도착 이벤트 공급 경계 |
| `platform/ParkingStateProvider.kt` | 주차 상태 공급 경계 |
| `ui/` | 화면·ViewModel·공통 자물쇠 컴포넌트 |
| `src/debug/` | 가짜 제공자와 개발 패널 |
| `src/release/` | 사용할 수 없는 외부 상태를 명시하는 제공자 구성 |
| `src/main/assets/demo_package.json` | 검증용 콘텐츠 |
| `src/test/`, `src/androidTest/` | 로직·저장·UI 검증 |

- UI는 상태를 표시하고 사용자 이벤트를 전달합니다. Composable 안에 정답·세션 전이·저장 로직을 넣지 않습니다.
- UI에서 보는 진행 상태의 기준을 하나로 유지합니다. 저장소 상태와 별개인 `solved`·`rewardGranted` 값을 여러 ViewModel에 중복 저장하지 않습니다. [S6]
- 도착 이벤트와 주차 상태는 앱 소유 타입으로 전달합니다. 향후 Pleos SDK 타입이 게임 로직 전체로 퍼지지 않도록 합니다.
- 개발 패널에서 발생시킨 도착 이벤트도 정식 이벤트 처리 경로를 통과해야 합니다.
- 데이터·ViewModel의 Flow는 화면 생명주기에 맞게 구독하고 중복 구독·무한 재수집을 피합니다.

| T04 | 정답 순서와 같은 기호를 다른 순서로 제출 | 오답; 정답 배열만 해결 |
| T05 | 조합값 하나만 일치 / 둘 다 일치 / 범위 밖 | 각각 오답 / 정답 / 형식 오류 |
| T06 | 성공 직후 빠르게 재제출 또는 이전 화면 이벤트 | 보상·오답·다음 경유지 상태가 중복 변경되지 않음 |
| T07 | 1번 완료 후 2번 미방문 상태로 시도 | 2번 방문 확인 전에는 플레이 불가 |
| T08 | 정답 보기 후 재시작, 이후 건너뛰기 | 공개 이력 복원; `SKIPPED`와 보상 유지 |
| T09 | 힌트를 반복 열고 앱 다시 시작 | 공개 단계 수가 중복 증가하지 않고 복원 |
| T10 | 퍼즐 도중 `DRIVING` 또는 `UNKNOWN` | 내용 가림, 제출·힌트·건너뛰기 차단; 복귀 후 재개 |
| T11 | 저장 완료 후 force-stop·재실행 | 진행·보상 복원, 주차는 `UNKNOWN`; 앱 데이터는 지우지 않음 |
| T12 | 저장 실패·손상 JSON·알 수 없는 버전 주입 | 자동 초기화·보상 중복 없음, 오류·재시도 또는 명시적 초기화 제공 |
| T13 | 이전 저장·제출 처리 중 새 게임 시도 | 이벤트 순서가 보장되고 이전 세션의 보상이 새 세션에 섞이지 않음 |
| T14 | 세 경유지를 해결 또는 건너뛰기 | 완료 화면에 상태·힌트 사용 수가 정확히 표시 |
| T15 | 네트워크를 끈 상태에서 새 게임부터 완료 | 전 과정 정상 동작 |
| T16 | release 빌드 실행 | 개발 패널 없음, 외부 상태 미연동으로 플레이 차단 |

최소 자동 검증은 T03~T07의 게임 규칙, 힌트·건너뛰기 상태, 저장·복원·중복 완료, 저장 실패를 포함합니다. 상태 조합과 게이트 전이는 순수 로직 테스트를 우선하고, 실제 DataStore round-trip 테스트와 대표 UI 흐름을 추가합니다.

권장 명령은 생성한 프로젝트의 실제 task에 맞춰 확인 후 실행합니다.

```powershell
# Windows PowerShell, 프로젝트 루트
.\gradlew.bat :app:assembleDebug :app:testDebugUnitTest :app:lintDebug
.\gradlew.bat :app:assembleRelease
# 실행 가능한 에뮬레이터가 있을 때
.\gradlew.bat :app:connectedDebugAndroidTest
.\gradlew.bat :app:installDebug
```

```bash
# macOS / Linux, 프로젝트 루트
./gradlew :app:assembleDebug :app:testDebugUnitTest :app:lintDebug
./gradlew :app:assembleRelease
# 실행 가능한 에뮬레이터가 있을 때
./gradlew :app:connectedDebugAndroidTest
./gradlew :app:installDebug
```

`adb devices`로 테스트 대상을 확인합니다. 여러 기기가 연결된 경우 대상 AVD를 명시해 다른 기기의 데이터를 건드리지 않습니다. 설치 후 런처에서 실제 진입 Activity를 실행해 확인합니다.

## 13. Codex의 작업·보고 원칙

- 사소한 파일명·색상·컴포넌트 배치 때문에 작업을 중단해 질문하지 않습니다. 이 문서의 기본값으로 구현하고 차이를 보고합니다.
- 실제 저장소를 확인하기 전에는 “빈 저장소”, “SDK 설치됨”, “에뮬레이터 연결됨”을 단정하지 않습니다.
- 필요한 환경 확인과 빌드 실패 수정까지 수행합니다. 사용자가 직접 고칠 코드 조각만 제시하고 끝내지 않습니다.
- 기존 파일 삭제, 기존 AVD 초기화, 의존성 전체 강제 업그레이드로 문제를 해결하지 않습니다.
- 특정 환경 요소가 막히면 그에 의존하지 않는 작업은 계속합니다. 사용자 입력이 반드시 필요한 경우 정확히 무엇이 없고 어떤 작업을 막는지 설명합니다.
- 실행하지 않은 테스트·에뮬레이터 검증은 `미실행`으로 표시합니다. Mock 통과와 실제 Pleos 동작 검증을 구분합니다.
- 공개 배포·스토어 등록·원격 저장소 업로드는 이 작업에 포함되지 않습니다.
- 최종 보고는 한국어 존댓말로 작성합니다.

납품물:

1. Android Studio에서 열 수 있는 전체 프로젝트와 정상 Gradle Wrapper.
2. 게임 기본 기능, 검증용 JSON, 관련 테스트.
3. `README.md`: 선택한 버전, 프로젝트 열기·빌드·설치, 시뮬레이션 조작, 실행 예시, 알려진 제한.
4. `docs/verification.md`: 실행한 명령과 결과, 사용한 AVD·API·화면 정보, T01~T16의 통과·실패·미실행 상태.
5. 빌드에 성공했다면 debug APK의 실제 경로. 빌드하지 못했다면 생성됐다고 주장하지 않음.

최종 설명은 구현 결과, 실제 검증 결과, 남은 환경 제약, 다음 단계에서 실제 연동할 지점을 짧게 정리합니다. 이번 작업은 서버 없는 기본 게임 기능이 완성되면 끝이며, 콘텐츠 제작이나 차량 제어로 자동 확장하지 않습니다.
